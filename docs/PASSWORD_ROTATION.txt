================================================================================
  Souvera Mail — Password Rotation
  Client Playbook + Operator Playbook (Admin section at the bottom)
  Introduced in: v0.18.1 (2026-02)
================================================================================

TL;DR
--------------------------------------------------------------------------------

Every device that logged in via
`/apps/souvera_mail/app-passwords/login-flow` should REPLACE its stored
credential periodically (default: every 90 days) — silently, in the
background, without user interaction.

The server publishes the desired cadence via `GET /apps/souvera_mail/me`
under `rotation.days`. Admins can override the cadence per-instance or
disable rotation entirely.

Rotation is 100 % client-driven — the server has no cron, no push,
no wake-up mechanism. The client checks the timer on app start and
whenever it comes to the foreground.

================================================================================
  WHY ROTATE
================================================================================

An app-password on Souvera Mail unlocks BOTH mail (IMAP/SMTP/Sieve) AND
Nextcloud (WebDAV, CalDAV, CardDAV). That's a very strong credential —
if the device is compromised (malware, stolen unlocked device, backup
leaked), the attacker holds full mail-and-files access until the token
is revoked.

Periodic rotation caps the exposure window without any user
interaction. Ninety days is a reasonable balance between "small enough
to matter" (industry-standard rotation policies pin 90 days from
NIST SP 800-63B annotations for high-value credentials) and "large
enough to be silent" (users won't notice a background HTTP call every
three months).

================================================================================
  ROTATION ALGORITHM (client)
================================================================================

Store TWO fields on the client alongside the app-password:

  - `appPasswordCreatedAt`  ISO-8601 UTC — server-supplied `createdAt`
                            from the login-flow response.
  - `stalwartId`            server-supplied — you need it to revoke.

On every app foreground (and on a periodic background job, if the
platform allows one), do:

  1. `GET <server>/apps/souvera_mail/me` with the CURRENT app-password
     as Basic-Auth. This is the ONLY reason `/me` exists.
     - If HTTP 200: read `rotation.enabled` and `rotation.days`.
     - If HTTP 401: the current password is dead (admin revoked it,
       user reset it). Do NOT auto-rotate — show a re-login screen.
     - If HTTP 5xx or network error: skip rotation this cycle and
       try again next foreground.

  2. If `rotation.enabled` is false, do nothing.

  3. Compute `ageDays = (now - appPasswordCreatedAt) in days`.
     If `ageDays < rotation.days - 3`, do nothing.
     (The `-3` fuzz avoids the whole fleet rotating in the same
      3-hour window when a batch of devices was provisioned together.)

  4. Rotate. In THIS EXACT ORDER — deviating leaves the user
     silently signed out if the network flaps mid-flow:

     a) POST `<server>/apps/souvera_mail/app-passwords/login-flow`
        with the CURRENT app-password as Basic-Auth. Body:
          {"description": "Souvera-android v1.0.2 (rotated 2026-05-20)"}
        Save the response fields to a temporary file / secure-storage
        entry (don't overwrite the live credential yet).
        The response has NEW `appPassword`, `stalwartId`, `createdAt`.

     b) Verify the new credential works: fire ONE test call —
        `GET <server>/apps/souvera_mail/me` with the NEW app-password.
        If HTTP 200, proceed. Otherwise: DELETE the new Stalwart
        password (see step d), retry the whole rotation next cycle,
        do NOT overwrite the live credential.

     c) ATOMICALLY replace the live credential with the new one:
        Android → EncryptedSharedPreferences.edit().apply()
        iOS     → Keychain SecItemUpdate
        Desktop → libsecret secret_password_store / DPAPI ProtectData

     d) Revoke the OLD Stalwart+NC pair — a single call cascades to
        both:
          DELETE <server>/apps/souvera_mail/app-passwords/<OLD_stalwartId>
        Auth for THIS call must use the NEW app-password (the old
        one you just supplanted may already be marked stale by
        Nextcloud's token store). Ignore 404 — it's fine.

  5. Log the rotation locally with anonymised metadata (device id,
     `ageDays`, `newStalwartId`). NEVER log the plaintext of either
     old or new secret.

================================================================================
  EXAMPLE — Kotlin / Android (OkHttp + coroutines)
================================================================================

    import okhttp3.Credentials
    import okhttp3.OkHttpClient
    import okhttp3.Request
    import okhttp3.MediaType.Companion.toMediaType
    import okhttp3.RequestBody.Companion.toRequestBody
    import org.json.JSONObject
    import java.time.Duration
    import java.time.Instant

    class SouveraCredentialStore(context: Context) { /* … see login-flow guide */ }

    class SouveraRotator(
        private val store: SouveraCredentialStore,
        private val client: OkHttpClient = OkHttpClient(),
    ) {
        /** Call on every app foreground. Suspends until done. */
        suspend fun tick() {
            val cred = store.load() ?: return
            val meResp = fetchMe(cred) ?: return  // network / auth error
            val rotation = meResp.getJSONObject("rotation")
            if (!rotation.getBoolean("enabled")) return

            val ageDays = Duration.between(
                Instant.parse(cred.createdAt),
                Instant.now(),
            ).toDays()

            val target = rotation.getInt("days") - 3
            if (ageDays < target) return

            val newCred = createNewAppPassword(cred, "rotated ${Instant.now()}")
                ?: return
            if (!verify(newCred)) {
                revoke(newCred)   // cleanup the freshly-created one
                return
            }

            store.save(newCred)
            revoke(cred)          // ignore-if-404 semantics
        }

        private fun fetchMe(cred: SouveraCred): JSONObject? {
            val req = Request.Builder()
                .url("${cred.server}/apps/souvera_mail/me")
                .header("Authorization", Credentials.basic(cred.loginName, cred.appPassword))
                .header("User-Agent", "Souvera-android/1.0.2")
                .build()
            return runCatching {
                client.newCall(req).execute().use { r ->
                    if (r.code == 200) JSONObject(r.body!!.string()) else null
                }
            }.getOrNull()
        }

        private fun createNewAppPassword(cred: SouveraCred, desc: String): SouveraCred? {
            val body = JSONObject().put("description", desc).toString()
            val req = Request.Builder()
                .url("${cred.server}/apps/souvera_mail/app-passwords/login-flow")
                .header("Authorization", Credentials.basic(cred.loginName, cred.appPassword))
                .header("User-Agent", "Souvera-android/1.0.2")
                .header("Content-Type", "application/json")
                .post(body.toRequestBody("application/json".toMediaType()))
                .build()
            return runCatching {
                client.newCall(req).execute().use { r ->
                    if (r.code != 200) return null
                    val j = JSONObject(r.body!!.string())
                    SouveraCred(
                        server      = j.getString("server"),
                        loginName   = j.getString("loginName"),
                        appPassword = j.getString("appPassword"),
                        stalwartId  = j.getString("stalwartId"),
                        createdAt   = j.getString("createdAt"),
                    )
                }
            }.getOrNull()
        }

        private fun verify(cred: SouveraCred): Boolean =
            fetchMe(cred) != null

        private fun revoke(cred: SouveraCred) {
            val req = Request.Builder()
                .url("${cred.server}/apps/souvera_mail/app-passwords/${cred.stalwartId}")
                .header("Authorization", Credentials.basic(cred.loginName, cred.appPassword))
                .delete()
                .build()
            runCatching { client.newCall(req).execute().close() }
        }
    }

    data class SouveraCred(
        val server: String, val loginName: String, val appPassword: String,
        val stalwartId: String, val createdAt: String,
    )

Wire it up in your Application/Activity foreground callback:

    override fun onResume() {
        super.onResume()
        applicationScope.launch(Dispatchers.IO) {
            SouveraRotator(credStore).tick()
        }
    }

  EXAMPLE — Swift / iOS
================================================================================

    import Foundation

    struct SouveraCred: Codable {
        let server, loginName, appPassword, stalwartId, createdAt: String
    }

    actor SouveraRotator {
        let store: SouveraKeychainStore

        func tick() async {
            guard let cred = store.load() else { return }
            guard let me = try? await fetchMe(cred) else { return }

            let rotation = me["rotation"] as? [String: Any] ?? [:]
            guard let enabled = rotation["enabled"] as? Bool, enabled else { return }
            let days = rotation["days"] as? Int ?? 90

            let createdAt = ISO8601DateFormatter().date(from: cred.createdAt) ?? Date()
            let ageDays = Calendar.current.dateComponents([.day], from: createdAt, to: Date()).day ?? 0
            if ageDays < (days - 3) { return }

            guard let newCred = try? await create(cred, "rotated \(Date())") else { return }
            guard (try? await fetchMe(newCred)) != nil else {
                try? await revoke(newCred); return
            }
            store.save(newCred)
            try? await revoke(cred)
        }

        // fetchMe(_:), create(_:_:), revoke(_:) implementations
        // follow the same shape as the Android example.
    }

Trigger from `applicationWillEnterForeground`:

    NotificationCenter.default.addObserver(
        forName: UIApplication.willEnterForegroundNotification,
        object: nil, queue: .main
    ) { _ in Task { await rotator.tick() } }

================================================================================
  EXAMPLE — Rust / Desktop (tokio + reqwest)
================================================================================

    use chrono::{DateTime, Utc};
    use reqwest::Client;
    use serde::{Deserialize, Serialize};

    #[derive(Serialize, Deserialize, Clone)]
    pub struct SouveraCred {
        pub server: String, pub login_name: String, pub app_password: String,
        pub stalwart_id: String, pub created_at: String,
    }

    pub async fn rotate_if_needed(store: &Keyring) -> anyhow::Result<()> {
        let Some(cred) = store.load()? else { return Ok(()) };
        let client = Client::new();

        let me: serde_json::Value = client
            .get(format!("{}/apps/souvera_mail/me", cred.server))
            .basic_auth(&cred.login_name, Some(&cred.app_password))
            .send().await?.error_for_status()?.json().await?;

        let rot = &me["rotation"];
        if !rot["enabled"].as_bool().unwrap_or(false) { return Ok(()); }
        let days = rot["days"].as_i64().unwrap_or(90);

        let created = DateTime::parse_from_rfc3339(&cred.created_at)?;
        let age_days = (Utc::now() - created.with_timezone(&Utc)).num_days();
        if age_days < days - 3 { return Ok(()); }

        let new_cred: SouveraCred = client
            .post(format!("{}/apps/souvera_mail/app-passwords/login-flow", cred.server))
            .basic_auth(&cred.login_name, Some(&cred.app_password))
            .json(&serde_json::json!({ "description": format!("rotated {}", Utc::now()) }))
            .send().await?.error_for_status()?.json().await?;

        // Verify
        client.get(format!("{}/apps/souvera_mail/me", new_cred.server))
            .basic_auth(&new_cred.login_name, Some(&new_cred.app_password))
            .send().await?.error_for_status()?;

        // Atomic swap in keyring
        store.save(&new_cred)?;

        // Revoke old
        let _ = client.delete(format!("{}/apps/souvera_mail/app-passwords/{}",
            cred.server, cred.stalwart_id))
            .basic_auth(&new_cred.login_name, Some(&new_cred.app_password))
            .send().await;

        Ok(())
    }

Schedule with a `tokio::time::interval(Duration::from_hours(6))` loop
inside your background task, plus a `focus` DE-signal handler.

================================================================================
  FAILURE MODES — what the client MUST tolerate
================================================================================

  A) The user changed their NC password server-side while offline.
     - `/me` returns 401 with the current app-password.
     - Client MUST NOT try to rotate — the current password is dead.
     - Client SHOULD trigger re-login (SSO flow / login-flow).

  B) Network flap in the middle of rotation.
     - Between step 4a (create new) and 4d (delete old), the app has
       TWO valid credentials for a brief window. That is intentional.
     - If the app is killed mid-flow, on next start it will see the
       OLD credential is still stored, and try again. The stale-but-
       valid new credential will be reaped by the operator's
       automatic cleanup cron (see "Admin section" below).

  C) Server rate-limited us (429 Too Many Requests).
     - Back off with exponential delay. Never retry more than 3× per
     - foreground event.

  D) `rotation.enabled = false` (admin disabled).
     - Do not rotate, but continue calling `/me` on foreground so
       that if the admin re-enables it, the client picks up
       automatically on next check.

  E) User has been offline for > rotation.days.
     - Rotate immediately, exactly like any other overdue rotation.
     - Do NOT chain multiple rotations back-to-back — one per
       foreground event is enough.

  ADMIN SECTION — Operator playbook

================================================================================

CONFIGURE THE ROTATION CADENCE
--------------------------------------------------------------------------------

Server-wide default. Applied on all instances that share the same
NC config. Value is INTEGER, unit is DAYS.

  # Default: 90 days
  sudo -u www-data php /var/www/nextcloud/occ \
       config:app:set souvera_mail rotation_days --value=90

  # Aggressive: monthly (for regulated workloads)
  sudo -u www-data php /var/www/nextcloud/occ \
       config:app:set souvera_mail rotation_days --value=30

  # Relaxed: yearly
  sudo -u www-data php /var/www/nextcloud/occ \
       config:app:set souvera_mail rotation_days --value=365

  # DISABLED (clients will skip rotation entirely)
  sudo -u www-data php /var/www/nextcloud/occ \
       config:app:set souvera_mail rotation_days --value=0

  # Show current value
  sudo -u www-data php /var/www/nextcloud/occ \
       config:app:get souvera_mail rotation_days

  # Delete the config (revert to code default 90)
  sudo -u www-data php /var/www/nextcloud/occ \
       config:app:delete souvera_mail rotation_days

Clamped to `[1, 3650]`; values outside this window are logged as WARN
and clamped. Zero is the ONLY "disabled" signal.

RATE-LIMIT IMPACT
--------------------------------------------------------------------------------

Rotation multiplies device traffic against `/apps/souvera_mail/*`.
Rough sizing: with 90-day rotation and 5000 active devices, expect
~55 rotations per day, spread uniformly (each device rotates on its
own timer). If you shorten to 30 days, that's 3× the traffic.

Sanity check — the Stalwart JMAP endpoint (`AppPassword/set` for
create + destroy) is called TWICE per rotation. Multiply by 2× for
back-of-envelope Stalwart QPS.

BRUTE-FORCE COUNTER TUNING
--------------------------------------------------------------------------------

Rotation calls arrive with valid Basic-Auth — they should NEVER hit
the brute-force counter. But if a device holds a stale credential
(admin revoked it while device was offline), it WILL start hitting
401s repeatedly. That triggers the counter.

Symptoms in nextcloud.log:

  {"level":"warning","message":"Bruteforce attempt on
   souvera_mail_login_flow from <ip> (attempts: 11)",
   "app":"core.bruteforce"}

Remediation:

  # See offenders (with the attempt counter)
  sudo -u www-data php /var/www/nextcloud/occ security:bruteforce:show

  # Reset a specific IP after user re-logged in successfully
  sudo -u www-data php /var/www/nextcloud/occ \
       security:bruteforce:reset <ip>

  # Optional — whitelist known-good network ranges (e.g. corporate
  # VPN egress) so mobile-app users on a shared NAT don't collide:
  sudo -u www-data php /var/www/nextcloud/occ config:system:set \
       bruteforce.whitelist.0 --value="203.0.113.0/24"

  # Increase the threshold (default is 10 fails in 12h):
  # This is a NC-global setting, not app-specific — proceed with care.
  sudo -u www-data php /var/www/nextcloud/occ config:system:set \
       auth.bruteforce.protection.testing --value="true"

MONITORING — WHAT TO GRAPH
--------------------------------------------------------------------------------

Access log (nginx / caddy):

  - Count POST /apps/souvera_mail/app-passwords/login-flow per hour
    → this is your rotation-plus-first-login rate. Sudden spikes
      often mean a fleet-wide deploy just happened.

  - Count DELETE /apps/souvera_mail/app-passwords/* per hour
    → should track the POST rate roughly 1:1 in steady state.
      A DELETE-heavy ratio means clients are creating-then-abandoning
      credentials (e.g. verify-step failing).

  - Count GET /apps/souvera_mail/me per hour
    → this is your device-heartbeat rate. If it drops without a
      corresponding drop in user-count, something is broken client-side.

Log (nextcloud.log):

  # Grep for our warnings:
  grep -a 'Souvera Mail /me: .rotation_days.' /var/lib/nextcloud-data/nextcloud.log
  # Indicates admin-side config problems (typos, out-of-range values).

  grep -a 'Souvera Mail login-flow' /var/lib/nextcloud-data/nextcloud.log
  # Indicates client-side failures during rotation.

STALE-TOKEN CLEANUP
--------------------------------------------------------------------------------

If a client crashes mid-rotation, the freshly-created "new" credential
may be orphaned (never verified, never stored). It sits in Stalwart
and NC's `oc_authtoken` until:

  a) The user manually revokes it from `/settings/user/security`; or
  b) The nightly `MigrationCleanup` cron sweeps it — but that job only
     targets migration-scoped passwords, NOT rotation-orphans.

If you observe drift, sweep manually:

  # List a user's app-passwords with age:
  sudo -u www-data php /var/www/nextcloud/occ user:report | \
      grep 'App password'  # (dry-run — actual command varies by NC ver)

  # There is no built-in "old app-password prune" in this version.
  # Roadmap item: `occ souvera_mail:apppasswords:prune --older-than=Nd`
  # (see backlog in memory/PRD.md — P2).

DISABLING ROTATION IN AN EMERGENCY
--------------------------------------------------------------------------------

If rotation causes an incident (e.g. Stalwart is under maintenance
and can't accept new App-Password/set calls), set rotation to
disabled and clients will honor it on next foreground:

  sudo -u www-data php /var/www/nextcloud/occ \
       config:app:set souvera_mail rotation_days --value=0

Clients see `rotation.enabled = false` and pause. When the incident
is resolved, re-enable:

  sudo -u www-data php /var/www/nextcloud/occ \
       config:app:set souvera_mail rotation_days --value=90

No client restart required — the `/me` heartbeat picks it up.
